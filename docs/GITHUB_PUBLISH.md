# Выгрузка NAS Backup Manager на GitHub

Репозиторий: https://github.com/redn1ghtz/NAS_Backup_Manager

Подготовленная папка: `github-upload/0.1.0-alpha/` в рабочем проекте.
Ничего не отправляется автоматически: публикацию выполняет владелец аккаунта.

## 1. Что куда загружать

```text
github-upload/0.1.0-alpha/
  repository/           Содержимое для корня репозитория, вкладка Code
  release-assets/       Готовые EXE/ZIP и SHA256SUMS для GitHub Release
  RELEASE_NOTES.md       Готовый текст описания релиза
  PUBLISH_GITHUB_RU.md    Эта инструкция
  PUBLICATION_REPORT.json Проверка состава и исключённых материалов
```

**В Code** отправляйте содержимое `repository`, а не саму внешнюю папку.
После загрузки README.md, LICENSE, Cargo.toml, apps/, crates/, scripts/, docs/
должны оказаться в корне проекта, без дополнительного уровня `repository/`.

**В Release** прикрепляйте все файлы из `release-assets`, без изменений имён.
Не отправляйте их в Code. Локальные portable-папки оставлены без архивирования
для повседневных тестов; ZIP подготовлены отдельно для скачивания с GitHub.

В исходный комплект не входят node_modules, target, dist, пользовательские data,
SQLite, журналы, .env, исполняемые сборки и локальные инструкции агенту. Не включены
скриншоты QA с локальными путями, сторонний дизайн-референс с непроверенными правами
распространения и генерируемый граф. Иконки приложения, нужные для сборки, включены.

В `docs/DEPENDENCY_LICENSES.md` находится снимок лицензионных метаданных.
Архив third-party-licenses содержит также доступные локально тексты лицензий.
Это техническая инвентаризация, не заключение о соблюдении всех условий:
перед публичной публикацией просмотрите её ограничения и THIRD_PARTY_NOTICES.md.

## 2. Рекомендуемый способ: GitHub Desktop

1. Установите [GitHub Desktop](https://desktop.github.com/) и войдите в redn1ghtz.
2. Выберите **File → Clone repository → URL** и вставьте адрес репозитория.
3. Укажите отдельную папку, например `Documents/GitHub/NAS_Backup_Manager`, и
   клонируйте репозиторий. Не используйте рабочую папку с target и portable.
4. Откройте папку клона через меню Repository. Скопируйте в неё **содержимое**
   подготовленной `repository`, включая `.gitignore` и `.gitattributes`.
   Не копируйте и не заменяйте служебную `.git` клона.
5. В списке изменений просмотрите файлы. Если на сервере уже есть отличающиеся
   файлы, сравните их перед заменой; подготовка не предполагает удаления старой истории.
6. Создайте коммит с названием `Prepare 0.1.0-alpha` и отправьте изменения
   кнопкой **Push origin** (или публикацией текущей ветки для пустого репозитория).
7. Откройте вкладку Code на GitHub: README должен показываться сразу, а apps/
   и crates/ должны находиться на верхнем уровне.

При защищённой основной ветке создайте отдельную ветку, отправьте её и внесите
изменения через pull request. Не обходите защиту и не используйте force push.
Инструкция: [клонирование в GitHub Desktop](https://docs.github.com/en/desktop/adding-and-cloning-repositories/cloning-and-forking-repositories-from-github-desktop).

## 3. Альтернатива: командная строка

Сначала клонируйте репозиторий в отдельную папку:

```powershell
git clone https://github.com/redn1ghtz/NAS_Backup_Manager.git
cd NAS_Backup_Manager
```

Скопируйте сюда содержимое подготовленной `repository`. Затем:

```powershell
git status
git diff
git add .
git diff --cached --stat
git commit -m "Prepare 0.1.0-alpha"
git push origin HEAD
```

Если Git не знает автора коммита, настройте своё имя и email по подсказке Git.
Используйте свой адрес или GitHub noreply, не вымышленный адрес. При ошибке
авторизации войдите через GitHub Desktop/Git Credential Manager; пароль аккаунта
в команду не вставляйте. При ошибке о новых удалённых коммитах сначала синхронизируйте
ветку и разберите конфликты; не выполняйте push --force.

## 4. Создание первого релиза

После того как исходники появились в основной ветке:

1. Откройте раздел **Releases** репозитория и начните создание нового релиза.
2. В выборе тега создайте **`v0.1.0-alpha`**. Target — ветка с загруженным коммитом;
   проверьте, что она содержит текущую версию, README и скрипты упаковки.
3. Заголовок: **`NAS Backup Manager 0.1.0-alpha`**.
4. Скопируйте содержимое `RELEASE_NOTES.md` в описание.
5. В область вложений перетащите **все 7 файлов** из `release-assets/`:

   ```text
   NAS-Backup-Manager-0.1.0-alpha-setup-x64.exe
   NAS-Backup-Manager-0.1.0-alpha-setup-x86.exe
   NAS-Backup-Manager-0.1.0-alpha-portable-x64.zip
   NAS-Backup-Manager-0.1.0-alpha-portable-x86.zip
   NAS-Backup-Manager-0.1.0-alpha-inno-scripts.zip
   NAS-Backup-Manager-0.1.0-alpha-third-party-licenses.zip
   SHA256SUMS.txt
   ```

6. Отметьте **This is a pre-release**. Не представляйте альфу стабильной версией.
7. Сохраните черновик, проверьте описание и дождитесь окончания загрузки вложений.
8. Когда всё готово, нажмите **Publish release**.

Релиз привязан к коммиту через тег. GitHub добавит архивы исходников автоматически:
они не заменяют готовые приложения. Не загружайте весь проект или source ZIP вместо
установщиков. Руководства: [создание релиза](https://docs.github.com/en/repositories/releasing-projects-on-github/managing-releases-in-a-repository),
[исходные архивы и вложения](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

## 5. Проверка после публикации

- Откройте страницу релиза и убедитесь, что есть 7 ваших вложений и пометка pre-release.
- Скачайте один portable ZIP и один установщик через страницу, а не из локальной папки.
- Сравните хеш скачанного файла с SHA256SUMS.txt:

  ```powershell
  Get-FileHash '.\NAS-Backup-Manager-0.1.0-alpha-setup-x64.exe' -Algorithm SHA256
  ```

- Распакуйте portable в новую тестовую папку. Внутри должны быть три EXE и portable.flag,
  без ваших задач, data или истории. Запустите и проверьте номер 0.1.0-alpha.
- Для тестовой установки сначала закройте другие окна и фоновые операции приложения.
  Помните: обычная установка использует конфигурацию текущего пользователя.
- Проверьте ссылки README на релизы, инструкцию и Issues.

## 6. Если загружать через браузер

На вкладке Code выберите добавление файлов и загрузите содержимое `repository`,
сохраняя вложенные каталоги. Для большого количества файлов удобнее Desktop:
в браузере ограничение — 100 файлов за загрузку и 25 MiB на один файл. Если используете
несколько загрузок, каждый раз проверяйте текущий каталог и итоговую структуру.
`.gitignore` не спасает от ручного добавления неподходящего файла через браузер.
Справка: [загрузка файлов](https://docs.github.com/en/repositories/working-with-files/managing-files/adding-a-file-to-a-repository).

## 7. Что не загружать

Не копируйте рабочий проект целиком. В Code не нужны `target`, `node_modules`,
`portable`, `releases`, `github-upload`, `.git` другой папки, SQLite, `data`,
пароли, секреты, EXE/ZIP и журналы. В Release не нужны compiler QA-фикстуры,
дизайн-референс, скриншоты проверки или локальные настройки приложения.

Не заменяйте файлы опубликованного тега изменёнными бинарниками без новой версии.
Для следующей версии обновите номер, соберите и проверьте новые файлы, создайте
новый коммит/тег и новые контрольные суммы. Если включены immutable releases,
окончательно проверьте вложения до публикации: замена файлов после неё ограничена.

## 8. Повторная подготовка комплекта

После изменения кода сначала пересоберите приложения и установщики по INSTALLER.md.
Для подготовки публикации нужны Python 3.11+, Cargo с локальным кешем зависимостей
и существующий package-lock.json. Необязательные npm-пакеты других платформ могут
присутствовать только в метаданных, без локально установленного текста лицензии.

```powershell
python scripts/prepare-github.py
```

Скрипт не скачивает зависимости и не отправляет ничего на GitHub. Если выходная
папка уже существует, он предложит выбрать другую через `--output-dir` вместо
удаления старого комплекта. После подготовки снова просмотрите состав и отчёт.
